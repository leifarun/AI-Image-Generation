# 后端部署指引（排队限流 + 豆包 API）

这份文档是给老板看的保姆级操作指南，所有步骤都是"复制粘贴、点按钮"级别，无需懂技术。

> 说明：Edge Function 的代码我已全部写好（在 `supabase/functions/process-task/` 目录），
> 下面要做的是把它"部署"到 Supabase 云端，并配置豆包密钥。

---

## 一、你需要先准备的一件东西：豆包 API Key

1. 登录火山引擎方舟：https://console.volcengine.com/ark
2. 左侧「API Key 管理」→ 创建 API Key（或查看已有的）
3. 复制这个 Key（形如一长串字符）——**这个 Key 是绝密，不要发给我，下面直接填到 Supabase 里**

## 二、部署 Edge Function（两种方式任选）

### 方式 A：Supabase 控制台粘贴部署（推荐，最简单）

1. Supabase 控制台 → 左侧 **Edge Functions** → **Create a new function**；
2. 名称填 `process-task`；
3. 在弹出的代码编辑器里，把本地文件 `supabase/functions/process-task/index.ts` 的**全部内容**粘贴进去；
4. 点 **Deploy**（部署）。

### 方式 B：命令行部署（可选，需要装 CLI，暂不推荐给老板）

略。优先用方式 A。

## 三、配置环境变量（Secrets，豆包密钥就放这里）

1. Supabase 控制台 → **Edge Functions** → 找到 `process-task` → **Secrets / Settings**；
2. 添加以下 **2 个**环境变量（Key 填左边，Value 填右边）：

| 环境变量名 | 填什么 |
|---|---|
| `ARK_API_KEY` | 你的火山引擎豆包 API Key（绝密） |
| `ARK_BASE_URL` | `https://ark.cn-beijing.volces.com/api/v3` |

3. 保存。

## 三·五、必须启用 pg_net（任务自动调度依赖）

如果任务每张图生成后停在「排队中」，或者提交后一直不开始，先到
**SQL Editor** 执行 `docs/db/0020_enable_pg_net.sql`。

检查公式：

```sql
select jobid, schedule, command, active from cron.job;
select jobid, start_time, status, return_message
from cron.job_run_details
order by start_time desc
limit 5;
```

`cron.job` 应有每 30 秒执行一次的 `process-task` 任务，
`cron.job_run_details.status` 应为 `succeeded`。
若出现 `schema "net" does not exist`，就是漏装 `pg_net`。

## 三·六、部署员工账号管理函数

在 **Edge Functions → Deploy a new function → Via Editor** 中创建函数
`manage-staff`，粘贴 `supabase/functions/manage-staff/index.ts` 的完整内容并部署。

该函数复用 Supabase 自动注入的 `SUPABASE_SERVICE_ROLE_KEY`，
无需在前端或额外 Secrets 中保存 service_role key。
调用者必须携带当前管理员登录 Token，函数会再次校验管理员身份。

上线前还需在 SQL Editor 执行：

- `docs/db/0019_staff_accounts.sql`
- `docs/db/0020_enable_pg_net.sql`
- `docs/db/0021_retry_clears_results.sql`
- `docs/db/0022_read_default_model.sql`

当前 `process-task` 针对 Seedream 5.5 将单张模型生成超时设为 90 秒。
多图仍按“一次调用只生成一张”执行，避免接近 Supabase Edge Function 的 150 秒总上限。

新建任务页的“预计调用成本”由前端 `src/constants/pricing.ts` 计算，仅作参考；
若更换默认模型后运营端估算未变化，检查 0022 是否已执行。

> 说明：`SUPABASE_URL` 和 `SUPABASE_SERVICE_ROLE_KEY` 是 Supabase 平台自动注入的内置变量，
> **不需要手动配置**（且系统禁止用 `SUPABASE_` 前缀，填了会报错）。我的代码会自动读取它们。

## 四、配置定时触发（cron，让任务自动排队处理）

1. Supabase 控制台 → **SQL Editor** → 新建查询，粘贴下面这段并运行：

```sql
-- 每 30 秒自动运行一次任务处理器（处理排队中的任务）
select cron.schedule(
  'process-task-every-30s',
  '30 seconds',
  $$
  select net.http_post(
    url := 'https://ldbzszotzuzmwwyzasmn.supabase.co/functions/v1/process-task',
    headers := '{"Authorization": "Bearer <你的 anon key>"}'::jsonb
  );
  $$
);
```

2. 把 `<你的 anon key>` 换成 Settings → API 里的 anon/public key。

## 五、执行数据库脚本（按顺序）

在 SQL Editor 依次运行这几个脚本（文件都在 `docs/db/` 目录）：

1. `0006_queue.sql` —— 任务领取函数（原子领取，防并发）
2. `0007_task_flow.sql` —— 任务状态流转触发器
3. `0013_fix_service_role_grants.sql` —— **关键修复**：授予服务端角色表权限 + 重写领取函数

> 如果之前已经跑过 0006，就用 0007 里的最新版 claim_next_task 覆盖即可（0007 已包含更新版）。
> **0013 必须执行**：它修复"任务一直卡在生成中"的问题（服务端角色缺表权限）。

## 六、任务卡在"生成中"怎么办（排查速查）

若新建任务后状态一直停在"生成中"不回退，按下面顺序检查：

1. 确认已运行 `0013_fix_service_role_grants.sql`（这是最常见原因：服务端角色缺表权限）。
2. Edge Functions 控制台 → `process-task` → **Logs**，看诊断日志：
   - `[诊断] SUPABASE_URL 存在: true` —— 应为 true；
   - `[诊断] SERVICE_ROLE_KEY 存在: true` —— 应为 true；
   - 出现 `permission denied for table tasks` —— 说明 0013 未生效，重跑一次。
3. 确认 `ARK_API_KEY` 已配好且账户有余额；日志里 `豆包 API 4xx` 是密钥/余额问题。

## 七、验证

1. 前端新建一个任务（填真实 ASIN + 卖点）；
2. 等 30 秒左右，刷新任务列表，看状态是否从"待抓取"→"抓取中/排队中"→"生成中"→"已完成"或"待补充/失败"；
3. 成功的话，任务详情里能看到生成的图片。

---

## 已知限制与风险（如实说明）

1. **亚马逊抓取**：有反爬机制，成功率不保证 100%，失败会自动转"待补充"，运营手动粘贴资料即可继续；
2. **豆包图片链接 24h 失效**：处理器已自动把图片转存到 Supabase storage，长期有效；
3. **cron 频率**：30 秒一轮，任务从提交到出图通常需要 1~2 分钟（含抓取+生成），属正常；
4. **费用**：豆包图片生成按量计费（约每张几美分），请留意火山引擎账户余额。
