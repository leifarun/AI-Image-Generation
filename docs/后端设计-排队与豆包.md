# 后端设计说明：排队限流 + 豆包 API + 亚马逊抓取

## 整体架构（通俗说明）

前端只管"提交任务、看结果"，真正的重活都在云端 Supabase 完成：

```
运营提交任务
   ↓（status = pending_fetch）
Edge Function「任务处理器」被触发
   ↓
1. 抓取亚马逊资料（标题/五点/图片）
   ├─ 成功 → 存进任务 → status = queued
   └─ 失败 → status = need_input（等运营手动补）
   ↓
2. 组装 AI 指令（把模板占位符换成真实资料）
   ↓
3. 排队限流：全局最多 N 个任务同时"生成中"，每分钟最多 M 次豆包请求
   ↓
4. 调用豆包 API 生成图片（密钥在 Edge Function Secrets 里）
   ├─ 成功 → 图片存 storage → 写 task_results → status = succeeded
   └─ 失败 → 重试 1 次 → 仍失败 → status = failed + 记录原因
```

## 关键技术决策

### 1. 豆包 API（已查官方文档确认）
- 地址：`https://ark.cn-beijing.volces.com/api/v3/images/generations`
- 认证：`Authorization: Bearer $ARK_API_KEY`
- 模型：`doubao-seedream-4-0-250828`（可配置）
- 关键参数：`prompt`（指令）、`image`（参考图，可选）、`response_format:"url"`、`size`
- 返回：`data[].url`（图片链接，24h 有效，需及时转存到 storage）

### 2. 亚马逊抓取
- 采用「自动优先 + 手动兜底」：Edge Function 尝试抓取，失败则置为 need_input 等运营补。
- 抓取方式：用公开的亚马逊商品页 HTML 解析标题/五点/图片。
- 风险如实说明：亚马逊有反爬，成功率不保证 100%，且需控制频率避免封 IP。

### 3. 排队限流
- 用 system_settings 表存参数：max_concurrent_tasks（默认2）、max_requests_per_minute（默认10）。
- Edge Function 每次被调用时，先检查当前"生成中"任务数是否超限，超限则不处理（等下次触发）。
- 触发方式：定时 cron（Supabase 支持）每 30 秒跑一次 + 任务提交后立即触发一次。

### 4. 密钥安全
- 豆包 API Key 存 Supabase Edge Function Secrets（服务端环境变量），前端永远接触不到。
